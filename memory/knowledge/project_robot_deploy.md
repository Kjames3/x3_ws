The physical robot host is `jetson`, IP is DHCP/variable (seen: 10.13.245.176; 10.13.197.88 on 2026-07-10; 10.13.245.150 on 2026-07-11 — always confirm the current IP with the user). Key-based SSH works directly: `ssh jetson@<ip>` (no password needed for SSH; sudo needs a password the user can supply).

The `jetson-mcp` `sync_code` tool runs `rsync <local_path> <remote_path>` WITHOUT a trailing slash on local_path, so it copies the local DIR *into* remote_path (nests it). To update a package in place, pass `remote_path` = the PARENT dir, e.g. local_path=`/home/kamren/x3_ws/src/yahboomcar_description`, remote_path=`/home/jetson/x3_ws/src` (NOT `.../src/yahboomcar_description`, which creates `.../yahboomcar_description/yahboomcar_description/` and leaves the real package stale so colcon builds the old files). rsync uses `--delete`, scoped to the transferred dir only (sibling packages untouched). After sync, `colcon_build` with `packages=<pkg>` and verify the install/share copy actually changed.

The robot runs from `/home/jetson/x3_ws` via the systemd service `x3_server` (restart: `sudo systemctl restart x3_server`; it has a ~10s ExecStartPre sleep + camera/ROS init, so allow ~40-90s and poll `systemctl show -p MainPID`). Its git checkout is on `main` but **diverged** from the user's local `/home/kamren/x3_ws` (different commits) — a plain `git pull` will not cleanly carry local edits, so fixes often have to be applied to both copies.

ROS2 DDS config (CORRECTED 2026-07-25): the running system now uses **plain default DDS multicast on `ROS_DOMAIN_ID=42`** — NOT the FastDDS discovery server. Verified by reading `/proc/<pid>/environ` of the live `x3_server` AND `Mcnamu_driver_X3`: both have ONLY `ROS_DOMAIN_ID=42` (no `ROS_DISCOVERY_SERVER`, no `FASTDDS_DEFAULT_PROFILES_FILE`, no `RMW_IMPLEMENTATION`). So `ros2 topic list` / `ros2 topic info -v` (graph introspection) WORK from a plain `ROS_DOMAIN_ID=42` shell. CAVEAT: an ad-hoc external subscriber/`ros2 topic echo`/`ros2 topic hz` on the Jetson could do DISCOVERY (list/info populated, pub/sub counts correct) but received ZERO DATA for EVERY topic (/scan, /odom, /cmd_vel) — a data-transport quirk of a late-joining participant. So to check "is a topic actually flowing", graph introspection is reliable but `echo`/`hz`/custom subscribers are NOT — don't trust a 0-message reading as proof of silence. (Older discovery-server env — `ROS_DISCOVERY_SERVER=127.0.0.1:11811`, `FASTDDS_DEFAULT_PROFILES_FILE=.../config/fastdds_tcp_server.xml` — is no longer in use as of this date.)

RESTART FRAGILITY (2026-07-25): `sudo systemctl restart x3_server` shuts down UNCLEANLY — `motion_loop` keeps calling `drive.move()`→`_cmd_vel_pub.publish()` while rclpy tears down, throwing `RCLError: publisher's context is invalid` then `terminate called without an active exception` (C++ abort). Repeated restarts can orphan the relaunched ROS2 bringup (two `Mcnamu_driver_X3` fighting over `/dev/ttyCH341USB0`) and/or desync the Rosmaster MCU serial, leaving `/cmd_vel` commands not reaching the motors (robot "connected but won't move"). A full POWER CYCLE of the robot clears it (resets both Jetson processes and the Rosmaster board). Latent bug worth fixing: stop `motion_loop` publishing before rclpy context teardown, and ensure the bringup subprocess is cleanly killed on shutdown. See [[project_lidar_mount]] (CBF blocks translation on close lidar/chassis returns — a SEPARATE possible cause, but power-reset ruled it out here). Depth comes from a separate node `/home/jetson/EE_244_Final_Project/robot/orbbec_depth_node.py` publishing `/camera/depth/image_raw` (16UC1 mm) at 10 Hz.

To inspect the running server's live state without ROS, connect to its WebSocket `ws://localhost:8081` on the robot and read `readout` messages (fields: `velocity_estimates`, `depth_image` (only populated after sending `{"type":"toggle_depth","enabled":true}`), `detections` (only populated after `{"type":"toggle_detection","enabled":true}`, defaults OFF and resets OFF on restart), etc.). See [[project_rviz_debugging]].

The Jetson wheels needed two NVIDIA libs that JetPack 6.2 doesn't ship — installed by extracting the NVIDIA sbsa redist archives into `/usr/local/cuda/{include,lib64}` + `ldconfig`: **libcusparseLt 0.6.3.2** and **libcudss 0.5.0.16_cuda12** (without them `import torch` fails: `libcusparseLt.so.0` / `libcudss.so.0 cannot open shared object file`). (Was, pre-2026-07-25: `torch 2.10.0+cpu`, CPU-only ~1.9 fps.) The active YOLO model is now `yolo26n` (80-class COCO, `0:person`) running from `yolo_models/default/yolo26n.pt`.
